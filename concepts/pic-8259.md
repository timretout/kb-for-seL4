# 8259 PIC (programmable interrupt controller)

> The PC's original interrupt controller, a pair of 8259A chips giving 15 IRQ lines through I/O ports; every x86 kernel, seL4 included, still has to remap and mask it at boot even when it uses the APICs instead.

## What it is

An 8259A takes eight interrupt request inputs, picks the highest-priority
one that is not masked, raises a single `INT` line to the CPU, and when
the CPU acknowledges, supplies an 8-bit **vector** number (the index into
the interrupt descriptor table, see
[x86 exceptions and system calls](x86-exceptions-syscalls.md)). The IBM
PC/AT wired two together, and every PC chipset and hypervisor has
emulated that pair since:

![Two 8259A chips in cascade: the slave takes IRQ 8 to 15 and its INT output feeds input 2 of the master, which takes IRQ 0 to 7 and raises INT to the CPU; the master is at ports 0x20 and 0x21, the slave at 0xA0 and 0xA1.](../images/pic-8259-cascade.svg)

*The red line is the cascade: the slave's interrupts reach the CPU only
through the master's input 2.*

The slave's output feeds the master's input 2 (the **cascade**), so there
are 15 usable lines and IRQ 2 is never a device. Priority is fixed by
default: 0 highest, then 1, then 8 to 15 (through the cascade), then 3 to
7. Each chip has two [I/O ports](io-ports.md): a command port (`0x20`
master, `0xA0` slave) and a data port (`0x21`, `0xA1`).

(This section is from memory of the 8259A datasheet, unchecked, except
where seL4's driver confirms the values.)

### Registers

Each chip holds three 8-bit registers, one bit per input:

| Register | Meaning | Access |
|---|---|---|
| IMR, interrupt mask | 1 = input masked | read and write the data port |
| IRR, interrupt request | input is asserting, not yet delivered | write `0x0A` to the command port (OCW3), then read it |
| ISR, in-service | delivered to the CPU, not yet ended | write `0x0B` to the command port, then read it |

### Initialisation: ICW1 to ICW4

Writing a byte with bit 4 set to the command port starts initialisation;
the chip then expects three more **initialisation command words** on the
data port.

| Word | Port | Master | Slave | Meaning |
|---|---|---|---|---|
| ICW1 | command | `0x11` | `0x11` | start; edge-triggered; cascade mode; ICW4 will follow |
| ICW2 | data | base | base + 8 | vector of input 0; low 3 bits come from the input number |
| ICW3 | data | `0x04` | `0x02` | master: bit mask of inputs with a slave (input 2); slave: its cascade identity (2) |
| ICW4 | data | `0x01` | `0x01` | 8086 mode, normal (not automatic) EOI |

The BIOS programs ICW2 as `0x08` and `0x70`, so IRQ 0 to 7 arrive as
vectors 8 to 15. In protected mode those are CPU exceptions (8 is double
fault, 13 general protection, 14 page fault). Every protected-mode kernel
therefore **remaps** the pair, conventionally to `0x20` and `0x28`, the
first vectors above the 32 reserved for exceptions.

### Operation: OCWs, masking, EOI

After initialisation, writes are **operation command words**:

- OCW1 is any write to the data port: the new IMR.
- OCW2 goes to the command port; `0x20` is the non-specific **end of
  interrupt** (EOI), which clears the highest-priority ISR bit and lets
  equal and lower priorities through again. An interrupt from the slave
  needs an EOI to the slave and then one to the master.
- OCW3 (`0x0A`, `0x0B`) selects IRR or ISR for the next read.

### Spurious IRQ 7 and 15

If an input drops between the chip raising `INT` and the CPU's
acknowledge cycle, the chip has nothing to report and answers with its
lowest-priority vector: IRQ 7 on the master, IRQ 15 on the slave. No ISR
bit is set for it, so the handler must read the ISR to tell a real IRQ 7
from a spurious one, and must not send an EOI for a spurious one (except
that a spurious 15 still set the master's ISR bit 2, which does need
one).

### Why APIC-era kernels still touch it

The [local APIC and I/O APIC](apic.md) replaced the 8259 for everything
it could not do (more than 15 lines, more than one CPU, level-triggered
PCI sharing done properly). But the 8259 pair is still there, comes out
of reset or firmware enabled and pointing at exception vectors, and its
`INT` output is still wired to the CPU (through the local APIC's `LINT0`
pin as an "ExtINT" interrupt). A kernel that ignored it could take a
stray timer tick as a double fault. So the standard sequence is: remap
it to harmless vectors, then mask all 16 inputs (`0xFF` to both data
ports), then enable the APICs. Remapping first means that even a
spurious IRQ 7 or 15, which masking cannot prevent, lands on a known
vector. The ACPI MADT's `PCAT_COMPAT` flag says whether a machine has
the pair at all (see [ACPI tables](acpi-tables.md)).

## In seL4

The driver is
[`src/plat/pc99/machine/pic.c`](https://github.com/seL4/seL4/blob/master/src/plat/pc99/machine/pic.c),
about a hundred lines:

| Function | Does |
|---|---|
| `pic_remap_irqs(interrupt)` | ICW1 `0x11`, ICW2 `interrupt` and `interrupt + 8`, ICW3 `0x04`/`0x02`, ICW4 `0x01`, then IMR 0 on both (all unmasked) |
| `pic_disable()` | writes `0xff` to both data ports |
| `pic_mask_irq(mask, irq)` | sets or clears one IMR bit |
| `pic_is_irq_pending()` | reads the master's IRR; non-zero means something waits |
| `pic_ack_active_irq()` | sends EOI `0x20` to the slave (IRQ 8 and up) and the master, skipping the EOI when IRQ 7 or 15 has no ISR bit, that is, when it was spurious |

`try_boot_sys` in
[`boot_sys.c`](https://github.com/seL4/seL4/blob/master/src/arch/x86/kernel/boot_sys.c)
always calls `pic_remap_irqs(IRQ_INT_OFFSET)` with `IRQ_INT_OFFSET` =
`0x20`, so PIC inputs become vectors `0x20` to `0x2f`. These are
`int_irq_isa_min` to `int_irq_isa_max` in
[`include/plat/pc99/plat/machine.h`](https://github.com/seL4/seL4/blob/master/include/plat/pc99/plat/machine.h),
and seL4 IRQ numbers 0 to 15 (`irq_isa_min` to `irq_isa_max`); IRQ
numbers for I/O APIC pins and MSIs start above them at `irq_user_min` =
16, which is vector 48 (`int_irq_user_min`).

What happens next depends on the build option `KernelIRQController`
([`src/arch/x86/config.cmake`](https://github.com/seL4/seL4/blob/master/src/arch/x86/config.cmake)):

- **`IOAPIC`** (the default; `CONFIG_IRQ_IOAPIC`): `pic_disable()` is
  called straight after the remap, before the local APIC is set up. The
  PIC is never touched again, and IRQ numbers 0 to 15 are unused. User
  level gets interrupts with `seL4_IRQControl_GetIOAPIC` and
  `seL4_IRQControl_GetMSI`, choosing a vector for each.
- **`PIC`** (`CONFIG_IRQ_PIC`): the PIC delivers the 15 legacy lines. The
  local APIC is still enabled and still supplies the kernel timer and
  IPIs; only device interrupts come through the 8259. User level claims
  a line with the generic `seL4_IRQControl_Get(irq)` with `irq` 0 to 15,
  there is no trigger-mode or polarity choice, and MSIs remain available.
  The hooks are in
  [`include/plat/pc99/plat/machine/interrupt.h`](https://github.com/seL4/seL4/blob/master/include/plat/pc99/plat/machine/interrupt.h):
  masking calls `pic_mask_irq`, acknowledging calls `pic_ack_active_irq`
  for IRQs up to `irq_isa_max`, and the pending-interrupt check consults
  `pic_is_irq_pending`. If the MADT lists I/O APICs anyway, boot prints
  "Detected N IOAPICs, but configured to use PIC instead" and carries
  on.

The PIC option exists for old or minimal machines and simple emulators;
real work uses `IOAPIC`. See [IRQ handling](../sel4/irq-handling.md) for
the user-level model.

## Gotchas

- `pic_remap_irqs` leaves every line **unmasked**. Between it and
  `pic_disable` (or, in PIC mode, until the kernel masks lines
  individually) interrupts are off at the CPU, which is what makes that
  safe.
- A machine with no 8259 at all (some UEFI-only "legacy-free" designs
  and minimal hypervisor machine models) just ignores the port writes;
  the remap is harmless there. The reverse fault is worse: forgetting to
  mask on a machine that has one.
- In PIC mode IRQ 2 is the cascade, and the [PIT](pit.md)'s IRQ 0 is a
  PIC line. In I/O APIC mode the PIT usually arrives on pin 2, not pin 0,
  by an MADT interrupt source override. The numbers do not carry over
  between the two modes.
- PIC mode cannot work with more than one core: the 8259 can only
  interrupt the boot processor (unchecked whether the build system
  forbids the combination).
- Hypervisors emulate the 8259 with varying care. Reading the ISR to
  detect spurious interrupts costs two port accesses, each a VM exit.
